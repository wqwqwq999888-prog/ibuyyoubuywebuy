# 鬥陣買網站建置、維運與使用手冊

> 最後整理：2026-08-27  
> 正式官網：<https://douzhenmai.com/>  
> 正式後台：<https://douzhenmai.com/admin/>

本手冊說明網站如何組成、使用的平台與連接關係、日常操作方式，以及日後修改或交接時必須注意的事項。**本文件不保存密碼、金流密鑰、Supabase secret key、Webhook secret 或存取權杖。**這些資料應放在組織的密碼管理器，並至少指定兩位可接手的管理者。

## 1. 系統總覽

```text
顧客瀏覽器
  ├─ 首頁 index.html ──公開唯讀──> Supabase products
  ├─ 結帳 checkout.html ─────────> Netlify Functions
  │                                  ├─驗證商品與金額──> Supabase
  │                                  ├─付款──────────> 綠界 ECPay
  │                                  └─訂單同步──────> Google Apps Script ──> Google Sheet / Email
  └─ 後台 admin/ ──登入與 RLS────> Supabase

GitHub main ──自動建置──> Netlify astounding-rabanadas-a0a6e1 ──> douzhenmai.com
```

網站不是 WordPress，也沒有傳統應用程式伺服器：首頁、結帳與後台是 HTML／CSS／JavaScript；需要保密金鑰或伺服器驗證的工作由 Netlify Functions 執行。

## 4. 資料與安全設計

### 4.1 商品

- `products` 是正式商品來源；前台只讀取 `enabled=true`。
- `product_no` 是穩定且不可重複的商品識別碼。購物車與訂單依它對應商品，不可拿排序位置當 ID。
- 後台可管理名稱、售價、成本、規格、說明、圖片、商品類型、組合內容、排序與上下架。
- 圖片存於 `product-images`；接受 JPG、PNG、WebP，單檔上限 5 MB。
- 組合商品以 `product_type=combo` 及 `combo_contents` 表示；主圖顯示區為正方形。

### 4.2 訂單

- Supabase `orders` 是主資料庫；Google Sheet 是操作方便的副本，不可反過來把 Sheet 當唯一資料來源。
- 瀏覽器傳來的商品名稱、售價與總額不可信。Netlify Function 會重新查詢已上架商品並驗證金額。
- 銀行匯款送出後建立訂單，初始狀態為「已匯款待確認／待出貨」。
- 綠界訂單先放入 `pending_ecpay_orders`，ReturnURL 驗證 CheckMacValue、成功代碼與金額後才建立正式訂單。
- 後台修改付款／出貨狀態時，Netlify Function 會驗證登入 JWT，再同步 Supabase 與 Sheet。

### 4.3 密鑰與環境變數

Netlify 正式環境至少需要：

```text
SUPABASE_URL
SUPABASE_SECRET_KEY
GOOGLE_SHEET_WEBHOOK_URL
GOOGLE_SHEET_WEBHOOK_SECRET
ECPAY_HASH_KEY
ECPAY_HASH_IV
```

Apps Script 的 Script Properties 至少需要與 Netlify 相同的 `WEBHOOK_SECRET`；依目前程式也可能需要 `SUPABASE_URL` 及 `SUPABASE_SECRET_KEY`（或舊名 `SUPABASE_SERVICE_ROLE_KEY`）。

安全規則：

- `admin/config.js` 與 `storefront-catalog.js` 只能放 publishable／anon key。
- `SUPABASE_SECRET_KEY`、ECPay HashKey／HashIV、Webhook secret 絕不可 commit、貼入聊天或放在瀏覽器程式。
- Supabase secret key 在 server 對 REST API 使用 `apikey` header；不可假裝成使用者 JWT。
- Secret 洩漏時需立即輪替，並同步更新 Netlify、Apps Script及所有外部回呼設定。

## 5. 管理後台使用手冊

### 5.1 登入

1. 開啟 <https://douzhenmai.com/admin/>。
2. 使用 Supabase Authentication 中已授權的管理員 Email／密碼登入。
3. 共用電腦使用完務必登出；不要把密碼交給不需要後台權限的人。

### 5.2 新增或修改商品

1. 進入「商品管理」，選「新增商品」或既有商品的「編輯」。
2. 商品編號只能用未使用的數字；建立後不建議更改。
3. 填寫名稱、售價、成本、規格、說明、單包／組合分類及排序。
4. 組合商品要填正確的組合內容；圖片建議使用正方形。
5. 新商品先保持「下架」，儲存後檢查內容和圖片。
6. 確認無誤再改為「上架」，於無痕視窗重新載入首頁確認。
7. 要停售時使用「下架」，不要直接刪除，以保留歷史訂單可讀性。

價格或上下架異動會使顧客舊購物車無法用舊價格下單，這是預期的安全保護。重大改價前應避開促銷高峰並通知客服。

### 5.3 物流管理

- 修改名稱、費用或啟用狀態前，先確認 `checkout.html` 是否仍有寫死的流程與綠界物流代碼。
- 物流顯示名稱需在首頁／結帳、後台及 Apps Script 保持一致。
- 超商選店回呼 URL、正式網域與綠界後台設定必須一起檢查。
- 7-ELEVEN／全家訂單確認為「已付款」後，可在訂單的配送資料欄按「建立綠界物流單」；系統會帶入商品金額、商品名稱、收件人姓名、手機、Email、門市代號與備註。
- 自動建單前需執行 `20260827000000_ecpay_logistics.sql`，並在 Netlify 設定 `ECPAY_LOGISTICS_SENDER_NAME`、`ECPAY_LOGISTICS_SENDER_PHONE`；如物流商店代號不同，再設定 `ECPAY_MERCHANT_ID`。
- 綠界物流單建立後不可再次按建立；若 API 逾時或結果不確定，先到綠界用廠商訂單編號查詢，不可直接重送。
- 黑貓宅急便尚未納入這個自動建單功能，仍依既有人工流程處理。

### 5.4 折扣管理

- 折扣類型可為固定金額或百分比；百分比輸入 `9` 代表九折。
- 設定最低消費、使用上限、開始／結束時間與啟用狀態。
- 上線前測試：未達門檻、剛好達門檻、過期、停用及金額不低於零。

### 5.5 團購管理

1. 先建立專屬折扣碼。
2. 再建立團購活動、團主、佣金比例和有效期間。
3. 複製團主報表連結；該連結含 report token，勿公開張貼。
4. 活動結束後停用，結算時以已付款訂單及合約規則複核。

### 5.6 訂單管理

- 付款狀態：待付款、已付款、已匯款待確認、付款失敗。
- 出貨狀態：待出貨、已出貨、已完成。
- 收到匯款時先核對訂單編號、後五碼與金額，再改付款狀態。
- 出貨後更新狀態並保存物流追蹤資料；不要把測試訂單當正式出貨。
- 如果後台成功但 Sheet 未更新，以 Supabase 為準，先查 Netlify Function log 與 Apps Script execution log，不要重複建單。

## 6. 正式修改與發布流程

### 6.1 一般程式修改

1. 從最新 `main` 建立功能 branch。
2. 修改程式與文件，新增或更新回歸測試。
3. 至少執行：

   ```bash
   node --check storefront-catalog.js
   node tests/admin-static-check.mjs
   node tests/orders-product-pricing-check.cjs
   git diff --check
   ```

4. Commit 並建立以 `main` 為 base 的 PR。
5. 只在 `astounding-rabanadas-a0a6e1` 的 Deploy Preview 驗收。
6. 確認 Checks、首頁、後台、購物車、結帳及必要的測試訂單。
7. 經負責人授權後 Merge；Netlify 由 `main` 自動 Production deploy。
8. 確認部署狀態為 `Production / main / Published`，再至 `douzhenmai.com` 做 smoke test。

不要用 Preview URL 對外宣傳；不要用手動 Trigger deploy 取代版本控制流程。

### 6.2 資料庫 migration

1. 先備份資料並確認 migration SQL 可重複／可回復策略。
2. 在測試或 Preview 相容環境先執行。
3. 檢查 RLS：匿名顧客只能讀取應公開的已上架商品；管理員才可寫入。
4. 正式執行後立即驗證後台登入、商品讀取、建單及狀態同步。
5. migration 檔必須 commit；不可只在 Supabase Dashboard 手動改而不留版本紀錄。

### 6.3 Google Apps Script 修改

GitHub／Netlify 部署**不會**自動更新 Apps Script：

1. 在正確的 Google Sheet 開啟「擴充功能 → Apps Script」。
2. 將 repo 的 `google-apps-script/order-fields.gs` 更新至既有 project。
3. 儲存後選「部署 → 管理部署作業 → 編輯 → 建立新版本」。
4. 更新既有 Web App deployment，保持原 `/exec` URL、執行身分與存取權限。
5. 不得在畫面或文件公開 Web App URL 與 secret。
6. 建立「請勿出貨」測試訂單，確認 Sheet、台北時間、物流名稱及 Email。

### 6.4 ECPay 修改

- 先判斷使用測試或正式環境，禁止用真實顧客卡片做不受控測試。
- Callback／ReturnURL 必須為公開 HTTPS，並對應正式網域或正確 Netlify Function。
- 任何欄位、編碼或網址變更後，都要重新驗證 CheckMacValue、金額及重放／重複回呼行為。
- HashKey、HashIV 輪替後立即更新 Netlify secrets；不要寫入 repository。

- 抽查訂單在 Supabase、後台與 Sheet 金額／狀態一致。

- 匯出或驗證 Supabase 備份與還原程序。
- 檢查 npm／外部 CDN／Supabase JS 版本及瀏覽器相容性。

### 建議後續改善

1. 將正式與測試 Supabase／ECPay 完全分離，避免 Preview 測試寫入正式資料。

## 9. 故障處理

| 現象 | 優先檢查 | 不要做 |
| --- | --- | --- |
| 首頁沒有新商品 | 商品是否 `enabled=true`、分類／排序、Supabase RLS、瀏覽器 session/cache | 不要直接改靜態陣列掩蓋資料問題 |
| 結帳說價格已更新 | 後台現價、舊購物車快照、商品是否下架 | 不要繞過 server 金額驗證 |
| 後台不能登入 | Supabase Auth 使用者、`admin_users`、RLS、網址與 publishable key | 不要把 secret key 放進前端 |
| 訂單在後台但 Sheet 沒有 | Netlify log、Webhook URL／secret、Apps Script execution | 不要重複建立同一訂單 |
| Email 沒收到 | Apps Script execution、寄件配額、垃圾郵件、收件 Email | 不要在 log 公開完整客戶資料 |
| 綠界付款未建單 | ReturnURL log、CheckMacValue、成功代碼、金額、pending order | 不要手動偽造已付款訂單 |
| 綠界模擬付款顯示未收到 `1|OK` | 確認 Production 已包含重複 callback 的 idempotent 處理，再查 `ecpay-return` Function log、訂單編號及金額 | 不要重複建立訂單或刪除已付款訂單 |
| Production 出錯 | Netlify deploy log、commit、環境變數；必要時依正式事故程序 rollback | 不要直接編輯 Production artifact |

發生事故時先記錄時間、訂單編號、commit、deploy ID 與錯誤訊息；遮蔽電話、Email、地址及 secrets 後再交給開發者處理。
